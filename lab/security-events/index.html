PROJECT 04 / SECURITY LAB / 2026

Security Event Detection &
Investigation Lab.

Generate a day of synthetic sign-in events, watch three explainable detection rules fire as the timeline replays, open any alert to see exactly which events triggered it and why, then change the thresholds and see precision and recall move. Every number on this page is computed in your browser from the events shown; nothing is pre-computed, estimated or sent anywhere.

i A defensive, educational simulator using synthetic events only: pseudonymous accounts, reserved documentation IP ranges (RFC 5737 and RFC 3849) and synthetic timestamps. It is not a production SIEM, not a threat-intelligence feed and not a certified security product. It never connects to real systems, never collects credentials and never scans anything. Scores on these synthetic scenarios do not establish real-world detection accuracy.

      HOW THE SCORES ARE DEFINED

      Precise, and deliberately modest.

      • True positive: an alert whose evidence includes at least one event from a scenario labelled suspicious. False positive: an alert whose evidence is entirely benign.
      • Precision = true-positive alerts ÷ all alerts. Undefined when no alert was raised, and shown as such rather than as 0 or 100%. Strict precision counts only alerts whose trigger event was itself planted as suspicious, so an alert raised on a victim's own routine sign-in after an attack counts towards precision but not towards strict precision.
      • Recall = suspicious scenarios touched by any alert ÷ suspicious scenarios. Undefined when the data contains no suspicious scenario. Strict recall additionally requires an alert whose trigger event belongs to the scenario, so a single attack event caught inside an alert raised on a victim's own later login does not count.
      • Missed scenarios are the false negatives. Benign flagged counts benign scenarios cited by a false-positive alert; a benign scenario cited only by a true-positive alert (for example the victim's routine login that completes a brute-force sequence) is not counted against the rules.
      • Imported data is scored only when every event carries a verdict; otherwise the scores are reported as unavailable. Events labelled with a verdict but no scenario form one pseudo-scenario per verdict, so recall over such data can only be 0 or 100%.
      WHAT THE SCORES DO NOT MEAN

      Synthetic performance only.

      The scenarios were written by the same person who wrote the rules, with the rules in mind. High precision or recall here shows that the implementation does what its definitions say on data shaped like these scenarios. It says nothing about detection rates against real adversaries, real traffic volumes, real shared infrastructure or real user behaviour, none of which this lab has seen. Treat the numbers as a demonstration of measurement, not as a measurement of security.

      04 / LOCAL IMPORT

      Bring your own synthetic events.

      Optional. Paste JSON or choose a local file to run the rules on your own synthetic events. Processing is entirely local: nothing is uploaded, stored or transmitted. The page requests nothing but its own files, and its content security policy forbids every other connection.

Every field is treated as untrusted text and is rendered as text, never interpreted as markup or code.

      SCHEMA

      Strict by design.

      An array of events, or an object with an events array. Unknown fields, malformed timestamps (including impossible dates such as 30 February), unknown outcomes, oversized strings, duplicate ids and non-documentation addresses are all rejected with the record number and the field named.

      "id": "e-00001",

      "source": "203.0.113.9",

    }
  ]

      • id optional (all or none); letters, digits, . _ : -, up to 64 characters.
      • time ISO 8601 with a zone, or ts as integer milliseconds; years 2000–2099.
      • outcome is success or failure; account up to 64 characters of A–Z a–z 0–9 . _ @ -.
      • source must be inside 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24 or 2001:db8::/32.
      • reason, scenario (with a verdict of benign or suspicious) are optional; labels must cover every event or none.

      05 / THE METHOD

      Three rules, stated exactly.

      Each rule is a sliding-window state machine over events sorted by time. The definitions below are the ones the code implements and the tests check; the thresholds in the panel are the only knobs.

      R1 / SOURCE-BASED, VOLUME

      Repeated failures from one source

      Raise an alert when one source produces at least T failed authentication events within any sliding window of W seconds. The window is inclusive: an event exactly W seconds before the current one counts.

      Once raised, the alert stays open and absorbs every further failure from the same source that arrives within W seconds of the previous one, so a long burst is one alert with a growing evidence list rather than hundreds of alerts. A pause longer than W closes the episode; a later burst raises a new alert.

      What it catches on this data: brute force against one account. What it also catches: a misconfigured client retrying an expired credential. The rule cannot tell them apart, and the page says so on every R1 alert.

      Subject
      Source address
      Counts
      Failures, any account
      Defaults
      5 failures within 60 s
      Work
      O(1) amortised per event
      R2 / SOURCE-BASED, BREADTH

      Password spraying

      Raise an alert when failures from one source target at least A distinct accounts within any sliding window of W seconds (inclusive). Repeated failures against the same account do not add to the count; a per-account counter inside the window keeps the distinct count exact as old events fall out.

      Episodes work as in R1: the alert absorbs further failures from the source while they keep arriving within W seconds of each other.

      What it catches on this data: one source trying many accounts, including accounts that do not exist. What it can also catch, with a low threshold or a wide window: a shared office gateway whose many legitimate users occasionally mistype their passwords.

      Subject
      Source address
      Counts
      Distinct accounts among failures
      Defaults
      5 accounts within 120 s
      Work
      O(1) amortised per event
      R3 / ACCOUNT-BASED, SEQUENCE

      Success following repeated failures

      Raise an alert when a successful authentication for an account is preceded, earlier in event order and within the previous W seconds (inclusive), by at least F failures for the same account. In account scope the failures may come from any source; in source scope only failures from the source of the success count.

      The first qualifying success raises the alert. Further successes for the same account that arrive within W seconds of the previous success, and the failures in between, are absorbed into it, so one incident is one alert rather than one alert per sign-in; a longer pause closes the episode. A failure and a success with the same timestamp are ordered by their position in the input, which the event table shows.

      Why the sequence is suspicious rather than proof: a guessed password produces failures then a success, and so does a user who mistypes a password and then remembers it. The rule reports an ambiguity worth checking, with the sources side by side, and explicitly does not claim that the account was compromised.

      Subject
      Account (and the source of the success)
      Counts
      Preceding failures
      Defaults
      3 failures within 600 s, account scope
      Work
      O(1) amortised per event
      EVENT PROCESSING

      Deterministic from end to end.

      • Ordering: events are sorted by timestamp, then by their position in the input. Equal timestamps therefore have a defined order, and the same input always yields the same alerts, whether it arrives sorted or shuffled.
      • Windows are inclusive, [t − W, t], evaluated at every event with amortised O(1) work: each event enters a per-source or per-account queue once and leaves it once.
      • Duplicates: identical events with different ids are two events; duplicate ids are rejected before anything runs.
      • Alert identity: alerts are numbered in trigger order (then rule order). Comparison mode matches alerts across threshold sets by incident: the same rule, the same subject and overlapping time spans, so three short episodes under a narrow window can match one long episode under a wide one.
      • Cost: O(n log n) to sort plus O(n) to detect, with every event cited by at most two episodes of a rule, so the alerts hold O(n) evidence even on adversarial input. The largest preset (about fifteen thousand events) is detected in tens of milliseconds on a laptop; the table is paginated, the timeline is binned, at most 3,000 alert spans are drawn and the alert list shows 200 alerts per rule at a time.
      SYNTHETIC SCENARIOS

      Labelled before the rules run.

      Each preset plants scenarios on top of routine sign-ins and labels every event with its scenario and a verdict, benign or suspicious. The labels are ground truth for scoring only; the detector reads timestamps, outcomes, accounts and sources, nothing else, and a unit test verifies that stripping or inverting the labels changes no alert.

        SAFE DATA HANDLING

        Local, synthetic, text-only.

        • Runs entirely in your browser; there is no backend, no telemetry, no analytics, no tracking and no external log collection. The content security policy allows no network connections and no inline code.
        • Accounts are pseudonymous strings generated from the seed. Sources come only from the reserved documentation ranges 192.0.2.0/24, 198.51.100.0/24 and 203.0.113.0/24 (and 2001:db8::/32 on import), which are never routed on the internet.
        • Imported JSON is parsed as data, validated against a strict schema with bounded sizes, and rendered with text nodes only. It is never evaluated, never stored and never sent anywhere; reloading the page discards it.
        LIMITATIONS

        What this lab does not claim.

        It is not a security information and event management system: it has no collectors, parsers, retention, correlation across log sources, enrichment, case management or alert routing. The three rules are deliberately simple and are not a detection catalogue. The synthetic scenarios are hand-written illustrations, not samples of real attacks, so precision and recall on them do not predict performance anywhere else. Nothing here has been validated against real-world attacks, and the page never says otherwise.

        06 / HOW IT IS BUILT

        Engine apart from rendering.

        The same constraints as the rest of this portfolio: plain HTML, CSS and JavaScript, a strict content security policy, no dependencies, no third-party code and no network access from the page.

        ARCHITECTURE

        A pure module and a thin UI.

        detection.js is a pure ES module with no DOM access: the seeded generator, the strict event schema, sorting with deterministic tie-breaking, the three streaming rules, the evaluation and the explanations. app.js owns the DOM: it runs the engine on the whole dataset, keeps a cursor into the sorted events for playback, and renders the timeline (SVG), the alerts, the investigation view, the paginated table and the scores from the engine's output. Thresholds, seeds and presets are state; every change re-runs the engine and re-renders from scratch, so the screen can never disagree with the data.

        ACCESSIBILITY

        Usable without a mouse or colour.

        Native controls with visible labels and focus rings, alerts as real buttons, an investigation view that receives focus when opened from the keyboard, live regions for status and table changes, tables with captions and column headers, a text summary of the timeline for screen readers, rule marks that carry digits as well as colour, and no motion unless a playback button is pressed.

        VERIFICATION

        Tested against definitions, not impressions.

        Node's built-in test runner checks the engine against hand-computed fixtures (inclusive window edges, threshold edges, identical timestamps, out-of-order input, episodes, scopes), against independent O(n²) reference implementations of each rule on random traffic, and against the synthetic ground truth across many seeds. Playwright browser tests exercise the page at desktop, tablet, mobile and narrow widths: playback, filters, thresholds, comparison, import validation, keyboard use, themes, reduced motion, console errors and overflow.

        REPRODUCE

        Run it yourself.

        Clone the repository, start any static file server at its root, open /lab/security-events/, and run npm test for the static checks and unit tests. lab/security-events/README.md documents the event model, the rule definitions, the scoring, the schema and the test matrix.
