FORMULAS — EXACTLY WHAT THE SIMULATOR COMPUTES

Seven lines of arithmetic.

Scenario revenue
R₁ = R₀ × (1 + v) × (1 + b)R₀ is the published R$15.84M; v and b are the volume and basket changes as fractions.
Scenario average order value
A₁ = A₀ × (1 + b)A₀ is the published R$159.33.
Scenario orders
N₁ = (R₀ ÷ A₀) × (1 + v)R₀ ÷ A₀ ≈ 99,416 orders, consistent with the published "99K" and the exported 99,441; the result is approximate because R₀ is rounded.
Scenario delivery rate
D₁ = D₀ + ΔdD₀ is the published 97.02%; Δd is in percentage points.
Scenario on-time rate
T₁ = T₀ + ΔtT₀ is the published 91.88% of delivered orders; Δt is in percentage points.
On-time share of all orders
D₁ × T₁The on-time rate is conditional on delivery, so the two rates multiply.
Order outcomes
delivered = N₁ × D₁ · on time = delivered × T₁ · late = delivered − on time · not delivered = N₁ − deliveredApproximate counts, rounded for display.
ASSUMPTIONS — AND WHAT IS NOT MODELLED

Deliberately simple.

  • Revenue scales with the product of the volume and basket factors: no price elasticity, no promotional cost and no cannibalisation are modelled.
  • Delivery and on-time rates are moved directly in percentage points, independently of volume: capacity effects are not modelled.
  • The on-time rate stays conditional on delivery, as the published measure defines it.
  • Customer counts, product mix and the monthly profile are not projected, because the README publishes no basis for them.
  • The baseline is the published rounded summary, so every scenario output inherits that rounding.

The ranges are bounded so that no rate can reach 100% and no projection strays far from the published scale: −50% to +50% volume, −30% to +30% basket, −15 to +2.5 points of delivery, −25 to +8 points of on-time performance.

04 / THE METHOD

SQL to Power BI, as the project documents it.

How the original project uses each tool, in the README's own terms, and the material you can inspect yourself: the README, the two screenshots, the annotated view, the Power BI file and the PDF export.

STEP 01 / SQL

Query the transactional data

SQL is the first tool the README names: querying and shaping the e-commerce transactional data before analysis. The README lists "data cleaning and transformation" among the skills demonstrated, without separating the SQL work from the notebook work, and this lab keeps that separation open rather than inventing it.

STEP 02 / GOOGLE COLAB

Transform in notebooks

Google Colab hosts the notebooks that clean and transform the data: the README names the tool and the skill, not the language or the steps. No notebook is published in the repository, so the lab describes the step and reproduces nothing from it.

STEP 03 / DIMENSIONAL MODELLING

Model facts and dimensions

Power Query and data modelling in Power BI Desktop produce the documented dimensional model: fact_orders, fact_order_items and fact_cohort_retention, six dimensions, and KPI_Measures. The README states that the relationships support filtering across dates, customers, products, sellers, payment methods and order statuses.

STEP 04 / DAX

Define the KPIs as measures

Five measures are published verbatim: a row count, a two-column sum, and three DIVIDE ratios with a zero fallback. The lab quotes them exactly, draws their lineage and names the three referenced measures whose definitions are not published.

05 / HOW IT IS BUILT

Engine apart from rendering.

The same constraints as the rest of this portfolio: plain HTML, CSS and JavaScript, a strict content security policy, no dependencies, no third-party code and no network access from the page.

ARCHITECTURE

A pure module and a thin UI.

model.js is a pure ES module with no DOM access: the transcribed published and exported figures, the derived arithmetic, the KPI, measure, table and report definitions, the scenario formulas with their validation, and the formatters. app.js owns the DOM: it renders every chart as SVG from the module's output, keeps the four levers as state, recalculates the scenario on every change and writes every piece of text with text nodes. The published figures in the markup are checked against the module by a unit test, so the page cannot drift from the engine.

PROVENANCE

Three labels, never mixed.

Published marks figures transcribed from the README; Exported marks data labels transcribed from the dashboard's PDF export; Derived marks arithmetic on those figures with the operation shown; Hypothetical marks every simulator output, which is also hatched in the charts. No monthly series, customer record or transaction is reconstructed, and no projection is presented as performance.

ACCESSIBILITY

Usable without a mouse or colour.

Native sliders with typed twins and visible labels, preset buttons with pressed state, live status announcements on change, charts that take focus and read each mark with the arrow keys, a table view under every chart, a data-model diagram made of real buttons, hypothetical marks distinguished by hatching and wording rather than colour alone, and no motion beyond what the visitor triggers.

VERIFICATION

Tested against the source, not impressions.

Node's built-in test runner checks the engine against hand-computed scenarios, inclusive and exclusive boundary values, every class of invalid input, the README's KPI table and DAX text quoted verbatim, the internal consistency of the exported figures, and the colour tokens' contrast in both themes. Playwright browser tests exercise the page at 320, 375, 768, 1280 and 1920 pixels: the simulator against the engine's own numbers, keyboard use, the model explorer, links, themes, reduced motion and the content security policy.
