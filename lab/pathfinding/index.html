PROJECT 03 / INTERACTIVE LAB / 2026

Interactive Robotics &
Pathfinding Lab.

Draw walls and weighted terrain on a grid, place a start and a target, then watch breadth-first search, Dijkstra's algorithm and A* explore the map one cell at a time. Every number on this page is measured from the run that just happened in your browser; nothing is pre-computed or estimated.

i This is a grid-based algorithm simulation, not a validated real-world robotics navigation system. The "robot" is an abstract agent on discrete cells with exact, deterministic costs: there are no sensors, no kinematics, no uncertainty and no continuous space.

02 / THE ALGORITHMS

Three searches, one grid.

All three explore the same graph: cells are nodes, legal moves are edges. They differ only in the order they take cells off the queue, and that order decides what they can guarantee.

01 / UNINFORMED, UNIFORM COST

Breadth-first search

Keeps a first-in, first-out queue. The start cell goes in; each dequeued cell enqueues every unvisited neighbour. Because the queue is FIFO, cells are expanded in order of their distance in moves, so the first time the target is dequeued it has been reached with the fewest possible moves.

BFS never looks at edge costs. On this grid that means it is only cost-optimal when every move costs the same: 4-directional movement with no terrain. Add terrain or diagonal moves and BFS still returns the fewest moves, but Dijkstra or A* can find a cheaper route. The lab reports the weighted cost of the BFS path so the difference is visible.

What you will see: a diamond (4 directions) or square (8 directions) wavefront spreading evenly from the start, ignoring terrain colours entirely.

02 / UNINFORMED, WEIGHTED

Dijkstra's algorithm

Keeps a priority queue ordered by g, the cheapest known cost from the start. It always expands the cheapest frontier cell, relaxes its neighbours (records a better cost and predecessor when found), and stops when the target is dequeued. With non-negative costs, a cell's cost is final the moment it is dequeued.

This lab implements the queue as a binary heap with lazy deletion: improved entries are pushed again and stale ones are skipped on pop. That keeps each operation O(log V) with no decrease-key bookkeeping.

What you will see: a wavefront that slows down through terrain, because entering a terrain cell costs five times more, and that flows around it when a detour is cheaper.

Order
g = cost so far
Optimal
Yes, for any non-negative costs
Time
O((V + E) log V)
Memory
O(V) arrays, up to O(E) heap entries (lazy deletion)
03 / INFORMED, WEIGHTED

A* search

Dijkstra with a sense of direction. Cells are ordered by f = g + h, where h estimates the remaining cost to the target. This lab uses the Manhattan distance for 4-directional movement and the octile distance for 8-directional movement. Both never overestimate (they are admissible) and never violate the triangle inequality along an edge (they are consistent), because every move costs at least its geometric length and the cheapest cell weight is 1.

With a consistent heuristic, A* returns a path of exactly the same cost as Dijkstra while usually expanding far fewer cells. Exact ties on f are broken by preferring the smaller h, then first-in order, which keeps runs deterministic.

What you will see: exploration leaning toward the target, growing wider only when walls force a detour. On an open grid A* heads almost straight there; in a maze it has to explore nearly as much as Dijkstra.

Order
f = g + h (admissible, consistent h)
Optimal
Yes, same cost as Dijkstra
Time
O((V + E) log V) worst case
Memory
O(V) arrays, up to O(E) heap entries (lazy deletion)
RULES OF THIS SIMULATION

Exactly what the robot may do.

  • Cells are open (weight 1), terrain (weight 5) or walls (impassable).
  • Moves: 4-directional steps have length 1. In 8-directional mode diagonal steps have length √2 ≈ 1.414.
  • Cost of a move = step length × weight of the cell being entered. The start cell's own weight is never paid; the target's is.
  • No corner cutting: a diagonal move is allowed only when both orthogonal cells it passes between are not walls, so the robot can never squeeze between two diagonally touching walls.
  • Termination: every search stops when the target is dequeued, which makes the "expanded cells" numbers comparable across algorithms.
READING THE NUMBERS

What each measurement means.

  • Path length: number of moves from start to target.
  • Path cost: sum of the move costs along the route, recomputed from the grid for BFS so its non-optimality on weighted maps is visible.
  • Expanded cells: cells dequeued and processed (the closed set), including the target. "Frontier" cells were discovered but never expanded.
  • Search time: wall-clock time of the pure JavaScript search, measured before any animation starts and including the cost of recording the trace. It depends on your device, browser and whether the code is already warmed up, so it is an observation, not a benchmark.
CORRECTNESS EVIDENCE

Tested, not asserted.

The algorithms live in a pure module with no DOM access, so the test-suite exercises exactly the code the page runs. Automated tests cover empty grids, dense obstacles, unreachable targets (the expanded set is compared with an independent flood fill), start equal to target, one-cell corridors, deterministic layouts of every size, cancellation mid-search, repeated edits, and a property check that A* and Dijkstra return equal optimal costs on 150 seeded layouts (75 weighted random fields and 75 perfect mazes) in both movement modes wherever a route exists. Every returned path is re-validated move by move against the rules above.

LIMITATIONS

What this lab does not claim.

It is not a robotics stack: no localisation, sensing, motion constraints, dynamic obstacles or continuous-space planning. The grid is static during a search, weights are fixed at 1 and 5, and the heuristics are tied to the grid metric. Timings are observations on your machine and are not comparable across devices. The page is a teaching and engineering demonstration, not a validated navigation system.

03 / HOW IT IS BUILT

Small surface, no dependencies.

The same constraints as the rest of this portfolio: plain HTML, CSS and JavaScript, a strict content security policy, and no third-party code, fonts, analytics or tracking.

ARCHITECTURE

Algorithms apart from rendering.

pathfinding.js is a pure ES module: grid model, neighbour rules, heuristics, a binary heap, the three searches written as generators, path validation and the seeded layout generators. app.js owns the DOM: it drains a generator into a trace, measures the time, then replays the trace with requestAnimationFrame so pause, resume, step and stop are just cursor operations on that trace.

ACCESSIBILITY

Usable without a mouse.

The grid is a keyboard-navigable ARIA grid with a roving tab stop that stays in view, every cell has a spoken description, outcomes are announced through a live region, controls are native buttons, radios, selects and sliders, the start, target, terrain, frontier and path states carry glyphs, patterns or outlines in addition to colour (expanded cells rely on a tested 3:1 luminance contrast), and the animation is off by default when your system asks for reduced motion.

VERIFICATION

Unit, browser and static checks.

Node's built-in test runner covers the algorithm module. Playwright browser tests run the page at desktop and mobile sizes, exercise the controls through the keyboard and the pointer, and check for console errors, horizontal overflow and broken links. The portfolio's offline integrity script verifies both pages' links, assets and policies in continuous integration.

REPRODUCE

Run it yourself.

Clone the repository, start any static file server at its root, open /lab/pathfinding/, and run npm test for the static checks and unit tests. The documentation in lab/pathfinding/README.md explains the model, the proofs behind the heuristics, the test matrix and how to add an algorithm or a new layout generator.
