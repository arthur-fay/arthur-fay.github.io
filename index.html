    A pre-registered rolling-origin protocol: seven models refitted at 822 historical origins for horizons of 1 to 30 days. The selected regression's error is 28% below seasonal naive and 11% below the best simple baseline (WAPE 9.2%), but that lead is not statistically established (Holm-adjusted p 0.054 against the baseline) and the 95% prediction intervals covered 92.1% of outcomes: failed calibration, kept in the record.

    • Backtesting
    • Diebold–Mariano tests
    • Calibration audit
  5. L2

    Models

    Seven forecasting models behind one interface: naive and seasonal-naive baselines, same-weekday mean and median baselines, seasonal exponential smoothing, the original project's regression and the ATLAS regression, compared under one protocol rather than tuned to a headline number.

    • Python
    • pandas
    • Forecasting
  6. L1

ATLASDecision Intelligence & Forecasting Research

A reproducible research platform for NYC 311 demand forecasting, uncertainty evaluation and hypothetical resource-allocation scenarios: a hash-verified data snapshot, seven models backtested under a pre-registered protocol, a contract-tested FastAPI service, a typed React dashboard and a tested deployment package, all held to explicit scientific release gates.

i Research only: forecasting gains are not established statistically (the lead over the best simple baseline has a Holm-adjusted p of 0.054); prediction intervals failed calibration; optimization assumptions are hypothetical. ATLAS is research on frozen data, not an operating city system.

Inspect the documented API ↗ Research platform · No public live ATLAS deployment
Problem
Can historical demand be modelled responsibly, with the uncertainty reported rather than hidden?
Architecture
A hash-verified snapshot of daily counts feeds leakage-guarded features and seven models; a rolling-origin backtest and a calibration audit evaluate them; a FastAPI service with 14 versioned endpoints, API-key authentication, request limits and a committed OpenAPI 3.1 contract exposes the committed results; a React 19 and TypeScript dashboard is typed from that contract; a Linux deployment package (immutable releases, a hardened systemd unit with watchdog and sandboxing, an nginx TLS proxy, automatic rollback) is tested end to end in a disposable Ubuntu container, not deployed.
Evidence
The backtesting protocol and results, the release gate, the API documentation with its committed OpenAPI contract, and the CI workflow: Ruff, strict mypy, 1,780+ pytest tests under a 90% coverage gate (96% recorded in the release gate's run), shellcheck, dashboard size budgets and byte-for-byte reproduction checks.
Limits
The forecasting lead is not robustly established; the 95% intervals covered 92.1% of outcomes (failed calibration); every planning parameter is hypothetical; the data end on 2026-06-30 and the archived projection was never scored. The static demo, datasets and NYC-derived charts stay unpublished. MIT-licensed original code is separate from NYC Open Data terms.

Plate 04 / SecurityDetection simulation · synthetic events only · tested

Security LabSecurity Event Detection & Investigation Lab

A defensive, browser-only laboratory for security monitoring: generate a day of clearly labelled synthetic sign-in events, replay the timeline, watch three explainable detection rules fire under configurable thresholds, open the investigation view behind every alert, and score the rules against the planted scenarios with precision and recall.

i Synthetic events only, computed locally: pseudonymous accounts, reserved documentation IP ranges, no real systems, no telemetry. Not a production SIEM, and scores on synthetic scenarios do not establish real-world detection accuracy. The preview is a real run on a seeded “card” dataset (seed 13) and is regenerated by the test-suite.

Explore the security investigation lab → Interactive · Synthetic events only
Problem
Show how detection rules behave, and how thresholds trade precision for recall, without touching a single real log line.
Architecture
A pure engine module generates seeded scenarios, enforces a strict schema, runs three sliding-window rules and scores them; the UI renders the SVG timeline, the alerts, the investigation view, the table and the comparison.
Evidence
The detection engine, the methods and tests, including independent reference implementations of the rules.
Limits
Toy rules on synthetic scenarios: not a SIEM, not threat intelligence, not a measure of real-world accuracy. Nothing is stored or transmitted; local JSON import is strictly validated and never rendered as markup.

A closer look at ATLAS

Research with the uncertainty left in.

Good engineering is not only about what a system can do. It is also about what its evidence can actually support, and ATLAS keeps the parts that did not validate in the record.

01 — Question

Can historical demand be modelled responsibly?

ATLAS investigates historical NYC 311 request counts through a reproducible backtesting pipeline and documented model comparisons.

02 — Engineering

Build the system around reproducibility and contracts.

A hash-verified data snapshot, leakage-guarded features and byte-for-byte verification of every committed result; a FastAPI service with 14 versioned endpoints, API-key authentication, request-body and in-flight limits, deadline-managed worker processes and a committed OpenAPI 3.1 contract; a React 19 dashboard typed from that contract, with keyboard-operable SVG charts and axe-core checks; a hardened systemd and nginx deployment package whose crash, rollback and reboot paths are exercised end to end in a disposable container. CI runs Ruff, strict mypy, 1,780+ pytest tests under a 90% coverage gate, shellcheck and the reproduction checks.

03 — Scientific result

Disclose what did not validate.

On the confirmation year the selected model's error is 28% below seasonal naive and 11% below the best simple baseline, but that lead is not statistically established: Holm-adjusted p 0.054 against the baseline, and borderline against seasonal naive once the test's size is corrected. The prediction intervals failed calibration. The system preserves these findings instead of hiding them.

04 — Boundaries

Separate scenarios from decisions.

The optimization component demonstrates mathematical techniques with hypothetical parameters; it does not make verified NYC resource recommendations.

04 / The method

How the work is specified.

Three working rules that every plate in this portfolio follows, from the research platform to the smallest lab.

Spec 01 /

Think in systems.

Connect data, analysis, interfaces and deployment as one structure instead of a pile of disconnected tasks. Every project here is drawn as layers for that reason.

Spec 02 /

Make it reproducible.

Clear sources, versioned inputs, seeded generators and repeatable builds, so that the same input produces the same result, and anyone can verify it.

Spec 03 /

State the limits.

Distinguish demonstrated results from assumptions, unverified claims and work still in progress. Every plate carries its boundaries next to its evidence.
