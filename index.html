Plate 01 / FlagshipResearch software · Python · FastAPI · React

ATLASDecision Intelligence & Optimization Engine

An end-to-end research platform for historical NYC 311 demand forecasting, uncertainty evaluation and hypothetical resource-allocation scenarios, built with reproducible data pipelines, an API, a tested frontend and explicit scientific release gates.

i Research only: forecasting gains are not established; prediction intervals failed calibration; optimization assumptions are hypothetical. ATLAS is historical research, not an operating city system.

Problem
Can historical demand be modelled responsibly, with the uncertainty reported rather than hidden?
Architecture
Versioned inputs and integrity checks feed Python analysis and model comparison; a backtesting protocol and calibration audit evaluate the models; a FastAPI service and a React dashboard expose the results, with deployment profiles prepared but unpublished.
Evidence
The backtesting protocol and results, the release gate and the full source repository.
Limits
Forecast improvements not robustly established; prediction intervals failed calibration; optimization hypothetical. The static demo, datasets and NYC-derived charts stay unpublished. MIT-licensed original code is separate from NYC Open Data terms.

Plate 03 / InteractiveAlgorithm simulation · JavaScript ES modules · tested

Pathfinding LabInteractive Robotics & Pathfinding Lab

A working, dependency-free laboratory for grid search: draw walls and weighted terrain, drag the start and target, then run breadth-first search, Dijkstra's algorithm or A* with animated exploration, pause and step controls, deterministic maze generation and results measured from each run.

i Grid-based algorithm simulation, not a validated real-world robotics navigation system. The preview above is drawn from a real A* run on a seeded 16 × 9 field and is regenerated by the test-suite.

Problem
Make three classic graph searches inspectable: watch what each one explores, measure the result, and reproduce any layout from a seed.
Architecture
A pure ES module holds the grid model, heuristics, binary heap and the searches written as generators; the UI module replays each trace with requestAnimationFrame inside a keyboard-navigable ARIA grid.
Evidence
The algorithm source, the methods and test matrix, and the lab itself, which measures every number live.
Limits
Discrete cells, fixed weights and a static grid: no sensors, kinematics, uncertainty or continuous space. Timings are observations on your device, not benchmarks.

Plate 04 / SecurityDetection simulation · synthetic events only · tested

Security LabSecurity Event Detection & Investigation Lab

A defensive, browser-only laboratory for security monitoring: generate a day of clearly labelled synthetic sign-in events, replay the timeline, watch three explainable detection rules fire under configurable thresholds, open the investigation view behind every alert, and score the rules against the planted scenarios with precision and recall.

i Synthetic events only, computed locally: pseudonymous accounts, reserved documentation IP ranges, no real systems, no telemetry. Not a production SIEM, and scores on synthetic scenarios do not establish real-world detection accuracy. The preview is a real run on a seeded “card” dataset (seed 13) and is regenerated by the test-suite.

Problem
Show how detection rules behave, and how thresholds trade precision for recall, without touching a single real log line.
Architecture
A pure engine module generates seeded scenarios, enforces a strict schema, runs three sliding-window rules and scores them; the UI renders the SVG timeline, the alerts, the investigation view, the table and the comparison.
Evidence
The detection engine, the methods and tests, including independent reference implementations of the rules.
Limits
Toy rules on synthetic scenarios: not a SIEM, not threat intelligence, not a measure of real-world accuracy. Nothing is stored or transmitted; local JSON import is strictly validated and never rendered as markup.

A closer look at ATLAS

Research with the uncertainty left in.

Good engineering is not only about what a system can do. It is also about what its evidence can actually support, and ATLAS keeps the parts that did not validate in the record.

01 — Question

Can historical demand be modelled responsibly?

ATLAS investigates historical NYC 311 request counts through a reproducible backtesting pipeline and documented model comparisons.

02 — Engineering

Build the system around reproducibility.

Versioned inputs, integrity checks, Python analysis, a FastAPI interface, a React dashboard, browser tests, and prepared deployment profiles.

03 — Scientific result

Disclose what did not validate.

The claimed forecasting improvement is not conclusively established, and the prediction intervals failed calibration. The system preserves these findings instead of hiding them.

04 — Boundaries

Separate scenarios from decisions.

The optimization component demonstrates mathematical techniques with hypothetical parameters; it does not make verified NYC resource recommendations.

Inspect the source repository ↗

NYC Open Data is independently attributed in the source project. No NYC-derived charts or datasets are hosted on this portfolio.

03 / The method

How the work is specified.

Three working rules that every plate in this portfolio follows, from the research platform to the smallest lab.

Spec 01 /

Think in systems.

Connect data, analysis, interfaces and deployment as one structure instead of a pile of disconnected tasks. Every project here is drawn as layers for that reason.

Spec 02 /

Make it reproducible.

Clear sources, versioned inputs, seeded generators and repeatable builds, so that the same input produces the same result, and anyone can verify it.

Spec 03 /

State the limits.

Distinguish demonstrated results from assumptions, unverified claims and work still in progress. Every plate carries its boundaries next to its evidence.
